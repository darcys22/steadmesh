Agent tools

For composable team coordination, native participant pools and versioned self-context, see Composable native teams.

Give the team ways to remember decisions, delegate work, follow up later and use connected services. This reference explains the tools available to seats and the permissions each call uses.

A seat can discover its tools and use them to work with the rest of the team. Calls go to the platform service, which authenticates the seat from its identity token and checks its current execution lease and capability manifest, built from your grants. The same checks apply whether the call comes through MCP, the CLI or HTTP; a seat cannot substitute another identity.

How seats call tools

TransportHowNames
MCP (Claude Code)steadmesh-tools mcp runs as a stdio MCP server inside the seatDots become underscores: memory_search, or mcp__steadmesh__memory_search in Claude Code
CLIsteadmesh-tools call <name> '<json>', steadmesh-tools listDotted names. Exit code 1 means a tool error; 4 means the caller's lease was fenced.
HTTPGET /v1/tools, POST /v1/tools/{name} on the platform serviceDotted names

The development registry contains 57 tools; each seat sees only those permitted by its policy. Results are JSON, capped at 16 KiB. List tools document their own pagination arguments.

Coordinate independent native teammates

These development-source tools use native team policy. Native teammates have independent identities, ordinary turns and private memory. They are separate from the execution-scoped workers below.

ToolArgumentsBehaviour
teams.discoverteam?, after?, limit? (1–50)Lists opted-in teams or a team’s participants. Discovery stays scoped to membership; can_message reflects explicit routes.
teams.missionteamReads the mission, revision, work store, review policy and whether this participant may refine it.
teams.refine_missionteam, expected_revision, expected_policy_revision, mission, reasonOnly explicit mission editors may refine the mission. Supply the numeric expected_revision and the mission.policy_revision string from teams.mission as expected_policy_revision. Both must match, rejecting concurrent edits and stale refinements after operator policy changes. This cannot change the operator’s envelope.
teams.poolteam, cursor?, limit? (1–50)Lists independent runtime pool participants, separate from legacy teams.get worker runs. Default limit 20; pass returned next_cursor to paginate.
teams.growteam, template, request_id (UUID)Admits one peer from an explicit full-seat template within pool and shared-budget bounds. Retries are idempotent; no requester authority is inherited.
teams.drainteam, member_idDrains an admitted member within policy bounds. Preserves handoff/private memory and releases unfinished claims; pool maximum includes draining members.
context.readrevision?Reads this participant’s current private context or a historical revision. Initial context is revision 0.
context.updatefield, text, expected_revisionUpdates instructions or summary only if the corresponding edit flag permits it. Revision check is required. Reviewed instruction policy refuses direct instruction updates and rollback; use a proposal instead.
context.rollbackfield, revision, expected_revisionRestores one permitted field from an existing saved revision (at least 1) as a new revision, never overwriting another field.

Current context and policy must match. Approval creates an author-and-approver-attributed revision for the next turn; rejection leaves context unchanged. Self-approval is always denied.
context.historybefore_revision?Returns up to 20 revision metadata records, latest first. Paginate using the last returned revision.

Direct context read/update/rollback/history tools are scoped to the caller’s own private context. Each field is limited to 4096 UTF-8 bytes and combined JSON-escaped fields to 14336 bytes. Changes apply next turn; operator role/template instructions, original task and policy remain authoritative. Memory grants are independent of context edit flags.

An opted-in team’s message limit requires a current active execution and counts outgoing sends and replies in that execution. It does not grant routes. Pool minimum means availability, not continuous model calls.

Delegate to a disposable worker

Keep a persistent seat's identity and workspace while a separate, bounded Pod handles an explicit task. Workers receive fresh workspaces and sessions, the parent's model and sandbox limits, and no tools by default. Results do not apply themselves. See the task-worker API and security contract.

ToolArgumentsBehaviour
tasks.startrequest_id (UUID), prompt, timeout_seconds?, tool_names[]?, input_files[]?, artifact_paths[]?Starts an idempotent child run during an active parent execution. By default, at most four workers with cleanup outstanding and sixteen per parent execution; enabled elastic-team policy supplies shared limits. Default timeout ten minutes, maximum twenty.
tasks.getid, artifact_path?Reads parent-scoped state, bounded output and returned artifact names. A single small file can be requested by path; use the runtime API for full files.
tasks.cancelidRevokes the child and requests removal of its temporary workspace. Durable results are retained. Cleanup produces a deduplicated parent notification.

Expand a temporary team

Seats enabled by elastic-team policy can request an entire temporary team from administrator-approved templates. Admission is all-or-nothing, with no waiting queue or partial teams. Workers share the parent execution's output budget, inherit its pinned model/runtime authorization and cannot spawn workers. See launch recovery and operational limits.

ToolArgumentsBehaviour
teams.templatesoptional template or afterLists up to 64 approved template names and limits; pass the returned next_after as after for another page. Select a template to inspect its tool ceiling and bounded instruction preview. Use before expansion.
teams.expandrequest_id (UUID), workers[] (unique letters/digits/hyphens/underscores name, template, task)Admits 1–32 required workers atomically within organization and execution limits. Each task has a prompt and optional timeout_seconds, tool_names, input_files and artifact_paths. Omitted timeout uses the smaller of 600 seconds and the policy ceiling. Tools narrow the template ceiling; omitted means none. The server assigns child request IDs. Identical retries reuse the team; changed payloads conflict.
teams.getidReads this seat's durable team, member names, worker IDs and states. Use tasks.get for individual results and artifacts.
teams.cancelidCancels unfinished members and revokes access. Capacity remains held until runtime cleanup is confirmed; results remain available.

  "request_id": "424a30ad-fd44-46f4-a3da-e7224d4ed290",
  "workers": [
    {"name": "research-evidence", "template": "researcher", "task": {
      "prompt": "Find evidence relevant to the current design decision.",
      "tool_names": ["memory.read", "memory.search"],

    }}

The runtime API exposes POST /v1/elastic-teams, GET /v1/elastic-teams/{id} and POST /v1/elastic-teams/{id}/cancel. Creation requires a real running parent execution and current lease generation. Reads are scoped to the parent seat. Admission checks output-budget headroom but does not guarantee per-worker token funding; concurrent callers may consume it before a worker's next model call.

Compare independent alternatives

Start several approaches from the same explicit handoff and text files, compare their separate results, then deliberately choose one. This is a portable context snapshot, not a clone of process memory or a working tree. No parent secrets or tool grants are copied. See the branching workflow and safety contract.

ToolArgumentsBehaviour
branches.startrequest_id (UUID), handoff, alternatives[] (name and prompt), input_files[]?, artifact_paths[]?, timeout_seconds?Creates two to four independent disposable runs atomically. Identical retries reuse the group; changed payloads conflict. Existing worker limits still apply.
branches.compareidReads this parent's group with current states, bounded output and error previews, artifact counts and complete-result hashes. Retrieve full results before choosing.
branches.selectid, task_run_id, expected_revision, expected_result_sha256Records a completed group member as the chosen result with revision and digest checks. Keeps choice history. Never applies files, merges a branch or cancels siblings.

Keep decisions and working notes

Use personal stores for a seat's own context and shared stores for plans, decisions and notes the team needs. The platform enforces access to each store. Records are addressed like files: each has a path that is unique among the store's live records, for example notes/plan.md or decisions/auth.md. Agents decide how to organise them. Search and listing are authorised before they run, so counts, paths and snippets from stores a seat cannot read are never revealed.

ToolArgumentsBehaviour
memory.storesnoneStores available to this seat and the operations allowed on each.
memory.liststore?, prefix?, order_by (name, created_at, updated_at), order, max_results (≤100), cursorRecords under a path prefix: path, kind, size, revision and author, without contents.
memory.readstore + path, or record_id; revision?, start_line?, stop_line?A record or a past revision. Line numbers are 1-based and inclusive; negative ones count back from the last line. Long reads return next_start_line.
memory.searchquery (full text, web-search syntax) or queries[] (literal substrings) with match_mode (any, all_on_same_line, all_within_lines + line_count), case_sensitive, context_lines (≤5); stores[], path_prefix, tags[], max_results, cursorFull-text results with snippets, or literal matches line by line with surrounding lines.
memory.writestore, path, text, tags[]?, source_refs[]?, expected_revision?Creates the note at the path, or replaces its text. With expected_revision it is a compare-and-swap (0 means it must not exist yet): if someone else changed it first the result is a conflict with the current revision, and nothing is overwritten. Replacing needs the revise permission.
memory.appendstore, path, textAppends to a note, creating it if needed. Concurrent appends never overwrite each other, which suits logs and running notes.
memory.archivelocator, expected_revisionHides a note from listing and search and keeps its history.
memory.publishlocator, destination, destination_path?, text? (a summary)An attributed copy into another store the seat can write. Provenance is recorded, and access to the original never changes.
memory.historylocator, max_results, cursorRevisions with their authors and lease generations, newest first.

Paths under work/ hold work items (below). They can be read and searched like any record, but only the work tools change them, so ownership and status rules cannot be bypassed with memory.write.

Track ownership for longer work

For a quick exchange, messages and shared notes may be enough. When several seats contribute to one task, or work continues over days, use a work item to keep the objective, acceptance criteria, owner, status, plan, dependencies and supporting results together. A seat records it in a shared store with the id <store>/W-<n>. Work items are optional, with no required sequence of statuses. Every change is revision-checked.

ToolArgumentsBehaviour
work.createstore, objective, acceptance[], depends_on[], links[], parent?, owner?Creates the item as ready, optionally assigned. Personal stores are refused.
work.get, work.listwork_id; or store?, owner? (seat key or me), status?The item with its log and current revision, or summaries with the current step.
work.claimwork_id, expected_revision, note?Takes an unowned item. If someone else owns it, the result is a conflict naming the owner; nothing changes.
work.update_planwork_id, expected_revision, plan[] of {step, status} (pending, in_progress, completed), explanation?Replaces the plan. At most one step is in progress. Only the owner, or the creator while the item is unowned, can change it.
work.updatework_id, expected_revision, status?, note?, evidence[]?, blocker?Anyone who can write the store may add notes and evidence. Only the owner, or the creator while unowned, changes status: ready, in_progress, in_review, blocked (needs a blocker), done (needs evidence) or cancelled. A finished item reopens as ready. On a board with required review, done also requires a valid separate-member approval matching the current evidence and objective.
work.reviewwork_id, expected_revision, approve, noteA different team member reviews owned, in_review work. Approval requires evidence and records a content digest. Rejection returns it to in_progress. The reviewer still needs ordinary store write authority.
work.refinework_id, expected_revision, objective, acceptance[], reasonAn explicitly authorized mission editor refines the current objective while retaining the original task in revision history. Invalidates review; finished or in_review work reopens as ready. Ordinary store authority is still required.
work.releasework_id, expected_revision, noteThe owner gives the item up for someone else to claim.

A restarted seat finds its unfinished work items in the recovery section of its bootstrap context. The organisation can optionally publish work items to a tracker (work_publication, see Configuration). The tracker is a view for people. Agents never depend on it.

Return to work on a schedule

Use an automation for a reminder, a follow-up or a recurring check on a service the seat can access. Each automation is a named instruction that the seat carries out on a schedule. It is stored by the platform, outside Terraform, and survives restarts. Each run queues a turn for the seat carrying the instruction, waking the seat if it has stopped.

ToolArgumentsBehaviour
automations.createname, instruction, and one schedule: in (a delay, e.g. 20m), at (local 2026-10-09T15:00 or RFC 3339), every (an interval, at least 1m) or time (HH:MM) with days? (mon…sun, weekdays, weekends, daily); timezone?, until?, max_runs?Saves the automation and returns it with a readable schedule and its next three runs in local time with their UTC offsets. A name already used by one of the seat's live automations is a conflict naming its id, so agents update instead of duplicating. At most 50 active or paused automations per seat.
automations.listinclude_completed?The seat's automations: schedule, status, next runs, last run and counts.
automations.updateid; any of name, instruction, status (active/paused), the schedule fields, until, max_runs (null removes a limit)Changes the automation. in, at or every replace the schedule; time, days and timezone adjust a time-of-day schedule and keep what is left out, so moving a weekday check to 10:00 keeps it on weekdays. Resuming does not replay runs that fell due while paused.
automations.deleteidStops it for good. A run already queued still arrives.
clock.nowtimezone?The current time in the seat's time zone or another.

Times of day are read in the seat's time zone: the organisation's timezone (default UTC), or for a representative its human's, set on the channel binding. Every turn's envelope also carries current_time in that zone, since a message may have waited before the turn starts.

How runs behave:

  • Who runs it. The seat that created it, with its own harness, model and permissions.
  • Busy seat. A run is queued like any message; if the seat is busy it runs afterwards.
  • Overlap. While the previous run is still waiting or in progress, the next occurrence is skipped rather than piled up, and counted in skipped_runs.
  • Downtime. Occurrences missed while the platform was down are not replayed. One catch-up run says how many were missed, then the schedule resumes at its next future occurrence.
  • Daylight saving. time follows the wall clock. A time that happens twice runs once, at the first; a time skipped when clocks go forward runs that much later (02:30 becomes 03:30). every counts elapsed time and ignores the clock.
  • Ending. A one-off completes after its run. max_runs counts runs queued; the automation completes after the last. No runs happen after until.
  • Duplicates. Each occurrence is queued at most once, even if the scheduler retries.
  • Retirement. A retiring seat's automations stop.

Work with connected services

ToolArgumentsBehaviour
connections.listnoneConnections this seat may use, with the granted operations and targets.
connections.invokeconnection, operation, params, idempotency_key?Runs a granted operation on a tracker or code host, such as project.create on Linear or pull_request.create on GitHub (platform delivery). Each call is recorded in the operation ledger. Reusing an idempotency key returns the recorded operation only for the same stable seat, operation, targets and canonical request. Other reuse is a conflict and never reveals the earlier result.
operations.getidOne recorded operation: status, receipt and result.

The adapter validates the operation's parameters and derives the same targets it will execute against, including defaults. Unknown or ambiguous target fields are rejected; an extra target cannot override an operation's real id, repo or other target. Every resolved target must be granted for that operation. Fields from separate grants are never combined to manufacture broader access.

Account-wide searches or lists with no concrete target require an unrestricted grant for the requested operation. A target-limited grant, including targets = ["*"], fails closed for those calls. Stricter validation can reject formerly accepted ambiguous calls: send only the documented fields for the selected operation.

Use these parameters to create and read projects, update tasks and follow comments in Linear:

  • project.create: {name, description, content, team_ids}. Team IDs default to the connection's team_id; every selected team must be allowed. description is limited to 255 characters.
  • project.read: {id} or {query, first}.
  • task.write: {title, description, team_id, project_id, state_id, assignee_id, priority}. Passing an id turns a create into an update. Creating requires access to the selected or default team; updating requires access to the task ID. A supplied destination project must also be allowed.
  • task.read: exactly one of {id}, {query} or {project_id}.
  • comment.write: {issue_id, body}.
  • comment.read: {issue_id, first}. The issue's comments with author and time, so agents can act on what people write in Linear.

Check what happened to an external action

StatusMeaning
succeededApplied, with an external receipt such as a project ID or issue identifier.
failedRejected and not applied.
unknownThe request may have been applied, but the response was lost. The platform tried to read the effect back and could not confirm it. It is never repeated automatically: the agent should check the tracker. Unknown operations are listed in the seat's recovery context after a restart.

Because Linear has no idempotency keys, created records carry a marker steadmesh-op:<operation id>. After a lost response, the gateway searches for that marker within the original destination and verifies the returned resource before confirming the first attempt landed. A moved record or an unverifiable destination remains unknown; the operation is not replayed.

Try the delivery flow with scripted tasks

The fake harness never calls a model. It reads each message body as a small script, for deterministic infrastructure tests and the run-from-source walkthrough. Lines that start with / are commands; a body without any commands gets the reply ack: <text>. Every tool call goes through the steadmesh-tools binary, the same path and authority a real harness has.

CommandEffect
/tool <name> [json]Calls a platform tool and records the result as output.
/reply <text>Replies to the triggering message.
/reportReplies with all output collected so far.
/file write <path> <text>, /file read <path>Writes or reads a file in the seat's workspace.
/delegate <seat> <text…>Sends the rest of the message to another seat. When the reply comes back, it is forwarded to the original human.
/task (as the first line of a message from a seat)Runs the remaining lines and replies to the sender with their output. If the task delegates further with /delegate, the downstream result is forwarded back instead, so a chain such as representative, lead, engineer, reviewer reports the end result.
/sleep <duration>Waits (up to 10m); useful for testing interruption.
/claim <text>Records an agent claim that a task is done. The platform treats this as information only.
/fail <text>Fails the turn technically.

Messages queued with wake: false that arrive with a turn appear in its output as queued message from <seat>: ….

For example, to delegate a tracker task from a human message:

/delegate eng_lead /task
/tool connections.invoke {"connection":"linear","operation":"project.create","params":{"name":"Onboarding"}}
