Acceptance status

Which acceptance scenarios from the design are proven, partially proven or still pending.

The design defines 27 acceptance scenarios (A01–A27); A28, retiring a busy seat, was added with seat retirement, so 28 are tracked. This page shows where each one stands, as of release v0.5.0. The detailed record, with test names, is tests/acceptance/RESULTS.md.

What has been proven, and how. The design does not allow the platform to be called usable on mocked connectors alone, so evidence is kept separate by source:

  • pass means proven on a local kind cluster with the deterministic harness and fake Slack, Linear and GitHub servers, or by integration suites against real Postgres, a Kubernetes API server, Terraform and the real harness binaries against a scripted model.
  • Real model endpoints and real GitHub: the completion demo has a recorded real-services run (8 October 2026) in which a Claude Code lead, a Codex engineer and a Pi reviewer passed readiness through their own models, collaborated, and opened a pull request that reached review. Slack and Linear were the in-cluster fakes in that run, and its key-rotation step was skipped.
  • Real Slack and Linear: no run of make live has been recorded yet. The scenarios marked live still need one.

How to reproduce

make test               # unit tests
make test-integration   # Postgres via testcontainers, envtest, Terraform acceptance, Claude Code feasibility
make e2e                # the full apply-to-conversation suite on a fresh kind cluster
make demo               # the mixed-harness completion demo; DEMO_MODE=live for real models and GitHub
make live               # real Slack, Linear and Claude (credentials required)

Known limitations of this release

  • Shared workspaces are validated but not yet mounted into seats.
  • Artifact storage and backup/restore are not implemented.
  • Deleting an organisation waits for the platform to revoke its capabilities. If the platform is permanently unavailable, deletion is blocked, and there is no admin override yet.
  • A readiness timeout on the first create taints the Terraform resource; untaint it after fixing the cause.
  • The example foundation stage, and the quickstart platform stage when tokens are given as variables, keep credential values in their own Terraform state.
  • Terminal chat queues replies for a disconnected user in memory only: at most 200, lost if the platform restarts.
  • Model key rotation has been tested with fakes, not yet against a real provider.
