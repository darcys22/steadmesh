Quickstart

Give a small engineering team a test repository and its first task. You'll connect a model, start the team and talk to your representative from the terminal. Slack is optional.

This page documents release v0.5.0. Steadmesh is early-stage software: check Status and limits for test coverage and known gaps, and read the security notes below before connecting real accounts.

Choose a path

PathYou getYou need
Clone the example (start here)Four seats on Pi: a representative, a tech lead, a senior engineer and a reviewer, working in one GitHub repository. You chat from the terminal with orgctl.A cluster (kind is fine), Terraform, kubectl, Go, an OpenAI-compatible model endpoint, and a GitHub token for one test repository. No Slack.

Model usage costs money. Your model provider bills every request a seat makes: the readiness probe each seat runs when it starts or its configuration changes, and every turn of work. Set spending limits with your provider before you start. Idle seats stop, but the cluster, database and volumes keep running until you remove them.

Credentials in Terraform state. The stage that turns your tokens into Kubernetes Secrets also stores them in its Terraform state, even though the variables are marked sensitive. In the example that is organisation/; with the quickstart modules it is platform/. Keep .env, terraform.tfvars and the state files private and out of version control (the example's .gitignore already excludes them). To keep the values out of Terraform entirely, create the Secrets yourself and reference them instead. See Where do API keys go?

Run the example organisation

darcys22/steadmesh-example is a complete organisation in a few small files you can read before applying. Terraform downloads the Steadmesh software itself: the provider from the Terraform Registry, and the platform chart and images from ghcr.io/darcys22/steadmesh.

platform/        stage 1: namespaces, Postgres and the Steadmesh chart
organisation/    stage 2: your keys, the seats, and who may talk to whom
  organisation.tf      the organisation itself
  instructions/*.md    plain-English instructions, one file per role
.env.example     the keys you provide

What you need

ItemNotes
Docker and kind, or another clusterAny cluster works if its CNI enforces NetworkPolicy (seats start only once their sandbox is verified; kind's default CNI, Calico and Cilium all qualify), it has a default StorageClass, and about 4 CPUs and 8 GB of memory are free.
Terraform 1.5+, kubectl and Go 1.27+Go installs orgctl, the command you chat with.
A model endpointAny OpenAI-compatible API that serves /v1/chat/completions: its base URL, a model name and an API key. See Which LLM does it use?
A GitHub repository and tokenA fine-grained personal access token for that repository only, with Contents, Pull requests and Issues set to read and write. Use a test repository: the token is delivered into the seats' sandboxes so they can run git and gh (see Sandbox delivery).

Start your team

  1. Clone the example.

    git clone https://github.com/darcys22/steadmesh-example
cd steadmesh-example

    The Steadmesh release is pinned in platform/main.tf (local.version), the provider version in organisation/main.tf, and the seat image in organisation/organisation.tf.

  2. Create a cluster. Skip this if you are using an existing cluster.

    kind create cluster --name steadmesh

  3. Add your keys. Fill in .env: the kubectl context (kind-steadmesh for the cluster above), the model endpoint, and the GitHub repository and token. Read the state warning above first.

    cp .env.example .env     # then edit .env
set -a; source .env; set +a

    Terraform reads each TF_VAR_<name> environment variable as the variable <name>. Run the source line again in any new terminal. Terraform only ever uses the context you name, never your current one.

  4. Install the platform.

    cd platform
terraform init
terraform apply

    This creates the steadmesh-system and steadmesh namespaces, Postgres, and the Steadmesh chart (the CRDs, the controller, the platform service, the egress gateway and the read-only console). It finishes with Apply complete! once the platform is running. There are two stages because the organisation is a custom resource that only exists once the platform is installed.

  5. Create the organisation.

    cd ../organisation
terraform init
terraform apply

    terraform apply returns once all four seats have passed their readiness checks, including a probe turn through Pi and your model. The first time, that takes a few minutes while the seat images are pulled. If a check fails, the error names the condition. See Checking readiness; a seat stuck on its sandbox check usually means the cluster's CNI does not enforce NetworkPolicy.

  6. Talk to your representative.

    go install github.com/darcys22/steadmesh/cmd/orgctl@v0.5.0
orgctl chat --context "$TF_VAR_kube_context" --user me
    Chatting with me's representative over terminal. Ctrl-D or Ctrl-C to leave.
you> Add a CONTRIBUTING.md to the repo explaining how to run the tests.

    The example's instructions have your representative pass the request to the tech lead, with the senior engineer and reviewer working towards a pull request. Ask for the pull request link and review the change when it is ready. Delegated work can take several minutes. If you leave the chat, its messages wait until you reconnect, but they are lost if the platform restarts. orgctl connects through kubectl port-forward and reads your login token from the terminal-credentials Secret that the organisation stage created. See How do I chat with my representative?

Choose a useful first task

Pick something small enough to review in one sitting. Include the repository, the outcome you want and how the team should check its work. For example:

  • Ask the engineer to document how to run the tests, and the reviewer to check the instructions against the repository.
  • Ask for a regression test around one function before attempting a wider refactor.
  • Ask the team to save its findings and open questions in shared memory so you can return to them in a later conversation.

Use a test repository and review proposed changes before merging. Your instructions guide the work; the declared grants and sandbox access determine what the team can actually reach.

Follow the work

The example enables the read-only console. In another terminal:

kubectl --context "$TF_VAR_kube_context" get agentseats -A
kubectl --context "$TF_VAR_kube_context" -n steadmesh-system port-forward deploy/steadmesh-console 8090
# then browse to http://127.0.0.1:8090

The console shows seats, messages, runs, work items and readiness; it cannot change the organisation. See How do I see the organisation working? and What does lease held mean?

Use Slack and the quickstart modules

For one representative per person in Slack, start from the quickstart modules in the main repository instead. Terraform downloads the darcys22/steadmesh provider from the Terraform Registry, the platform chart and images from ghcr.io/darcys22/steadmesh, and the modules from GitHub; no clone is needed.

You get one personal representative per person, plus an engineering lead and an engineer that representatives can delegate to. Seats run Claude Code on an Anthropic model by default. You can choose Codex or Pi for any seat with harness and seat_harnesses in organisation/terraform.tfvars; see Harnesses and models for the API each one supports. People can also chat from a terminal on this path; see Shape your organisation.

Start the team in Slack

  1. Get the quickstart. This copies two small Terraform roots into a new directory. platform/ installs Steadmesh, and organisation/ declares your agents.

    mkdir steadmesh && cd steadmesh
terraform init -from-module="github.com/darcys22/steadmesh//quickstart?ref=v0.5.0"

  2. Install the platform. Set kube_context and your tokens (or existing_secret_refs; see the comments in terraform.tfvars.example) in terraform.tfvars. Read the state warning above first.

    cd platform
cp terraform.tfvars.example terraform.tfvars
terraform init
terraform apply

    This creates the steadmesh-system and steadmesh namespaces, Postgres, the platform chart (the CRDs, the controller and the platform service) and the credential Secrets. It finishes with Apply complete! once the platform's pods are running.

  3. Declare your organisation. Set your Slack workspace ID and the people who get a representative.

    cd ../organisation
cp terraform.tfvars.example terraform.tfvars
terraform init
terraform apply

    This stage reads the cluster, namespace, images and secret references from the platform stage's state, so keep both directories together. terraform apply returns once every seat has passed its readiness checks; the first time takes a few minutes while the seat images are pulled.

  4. Talk to your representative. In Slack, open the app and send it a direct message. Your representative replies in the same DM, usually within a minute; delegated work takes longer, and the representative reports back when the team replies. Start by sharing a preference you want it to remember, giving engineering a specific question to investigate, or asking it to create a small project with Linear connected. If nothing arrives, check kubectl --context <your-context> get agentseats -A and the console.

Follow the work from the console

Set enable_console = true in platform/terraform.tfvars and apply that stage. Then forward the console:

kubectl --context <your-context> -n steadmesh-system port-forward deploy/steadmesh-console 8090
# then browse to http://127.0.0.1:8090

With orgctl installed, orgctl console --context <your-context> does the same.

Upgrade

Change the release everywhere it is pinned, then apply platform/, then organisation/:

  • In the example: local.version in platform/main.tf, the darcys22/steadmesh provider version in organisation/main.tf, and the seat image tag in organisation/organisation.tf. Or pull the example's latest commit.
  • With the quickstart modules: every ?ref=v…, steadmesh_version and the provider version.

Remove

Destroying the platform deletes the database. Both paths declare the organisation with data_retention = "retain", so destroying organisation/ keeps its database records and workspace volumes. Destroying platform/ deletes its namespaces, and with them Postgres and everything retained in it. Deleting the cluster removes the volumes too. Retention is not a backup: Steadmesh has no built-in backup or restore yet, so take your own (a Postgres dump does not include seat workspace volumes) before destroying anything you want to keep. GitHub personal access tokens you gave agents must be revoked at GitHub separately. See How do I take it down? and Where is the data stored?

Both paths use the same two directories. Check the context and directory first, then destroy the organisation, then the platform:

cd organisation && terraform destroy   # retires the seats; data retained
cd ../platform && terraform destroy    # deletes namespaces and the database
kind delete cluster --name steadmesh     # only if you created it for this

Keep a copy of both stages' state files until the destroy has finished. Do not delete state files to clean up after removing a cluster by hand.
