Quickstart

Install Steadmesh into your Kubernetes cluster from a published release, declare a small organisation, and talk to your representative in Slack. No clone needed.

Terraform downloads everything:

  • the darcys22/steadmesh provider from the Terraform Registry;
  • the platform chart and images from ghcr.io/darcys22/steadmesh;
  • the modules from GitHub.

You get one personal representative per person, plus an engineering lead and an engineer that representatives can delegate to. Seats run Claude Code on an Anthropic model by default. You can choose Codex or Pi for any seat with harness and seat_harnesses in organisation/terraform.tfvars; see Harnesses and models for the API each one supports.

This page documents release v0.5.0. Steadmesh is early-stage software: check Acceptance status for what has been proven, and read the security notes below before connecting real accounts.

What you need

ItemNotes
A Kubernetes cluster and a kubeconfig context for itA CNI that enforces NetworkPolicy, because seats start only once their sandbox is verified. kind's default CNI, Calico and Cilium all qualify. You also need a default StorageClass, and about 4 CPUs and 8 GB of memory free.
Terraform 1.5+ and kubectl
A Slack appGo to api.slack.com/apps, choose Create New App → From a manifest, and paste slack-app-manifest.yaml. Create an app-level token with connections:write (xapp-…), install the app and copy the bot token (xoxb-…). Note the workspace ID (T…) and each person's member ID (U…; profile → ⋮ → Copy member ID). See Connect real services for details.
A model API keyAn Anthropic key for the default Claude Code seats. Codex needs an OpenAI Responses endpoint; Pi can use Anthropic, OpenAI Responses or an OpenAI Chat Completions-compatible endpoint. See Which LLM does it use?
Optional: a Linear API key and team IDLets agents create projects and issues. Linear is optional: the organisation stays ready and keeps working when it is missing or down.

Model usage costs money. Your model provider bills every request a seat makes: the readiness probe each seat runs when it starts or its configuration changes, and every turn of work. Set spending limits with your provider before you start. Idle seats stop, but the cluster, database and volumes keep running until you remove them.

Credentials in Terraform state. If you put tokens in platform/terraform.tfvars, the platform stage writes them into Kubernetes Secrets and into its Terraform state, even though the variables are marked sensitive. Keep terraform.tfvars and the state files private and out of version control. To keep the values out of Terraform entirely, create the Secrets yourself and set existing_secret_refs instead (see the comments in terraform.tfvars.example). See Where do API keys go?

Install

  1. Get the quickstart. This copies two small Terraform roots into a new directory. platform/ installs Steadmesh, and organisation/ declares your agents. They are separate stages because the organisation's provider needs the platform's CRDs to exist before it can plan (why two stages?).

    mkdir steadmesh && cd steadmesh
terraform init -from-module="github.com/darcys22/steadmesh//quickstart?ref=v0.5.0"

  2. Install the platform. Set kube_context and your tokens (or existing_secret_refs) in terraform.tfvars. Read the state warning above first.

    cd platform
cp terraform.tfvars.example terraform.tfvars
terraform init
terraform apply

    This creates:

    • the steadmesh-system and steadmesh namespaces;
    • Postgres;
    • the platform chart, which holds the CRDs, the controller and the platform service;
    • the credential Secrets.

    Terraform only ever uses the context you name, never your current one. Tokens given as variables are stored in this stage's Terraform state, so keep the state private. The apply finishes with Apply complete! once the platform's pods are running.

  3. Declare your organisation. Set your Slack workspace ID and the people who get a representative.

    cd ../organisation
cp terraform.tfvars.example terraform.tfvars
terraform init
terraform apply

    This stage reads the cluster, namespace, images and secret references from the platform stage's state, so keep both directories together. terraform apply returns once every seat has passed its readiness checks, including a probe turn through its own harness and model. The first time, that takes a few minutes while the seat images are pulled. If a check fails, the error names the condition. See Checking readiness; a seat stuck on its sandbox check usually means the cluster's CNI does not enforce NetworkPolicy.

  4. Talk to your representative. In Slack, open the app and send it a direct message. Your representative replies in the same DM. Try:

    • asking it to remember a preference;
    • asking it to have engineering look into something;
    • with Linear connected, asking for a project for a small task.

    The representative answers in the DM, usually within a minute; delegated work takes longer and the representative reports back when the team replies. If nothing arrives, check kubectl --context <your-context> get agentseats -A and the console below. To chat from a terminal instead, see How do I chat with my representative?

Watch the agents work

Set enable_console = true in platform/terraform.tfvars and apply that stage. Then open the read-only console:

kubectl --context <your-context> -n steadmesh-system port-forward deploy/steadmesh-console 8090
# then browse to http://127.0.0.1:8090

With orgctl installed, orgctl console --context <your-context> does the same. The console is read-only: it shows seats, messages, runs, work items and readiness. See How do I see the organisation working? and What does lease held mean?

terraform plan lists the seats each change affects. Seats keep their identity, workspace and memory across applies. The tutorial explains every part of the declaration.

Upgrade

In your copy, change every ?ref=v…, steadmesh_version and the darcys22/steadmesh provider version to the new release. Apply platform/, then organisation/.

Remove

Destroying the platform deletes the database. The organisation is declared with data_retention = "retain", so destroying organisation/ keeps its database records and workspace volumes. Destroying platform/ deletes its namespaces, and with them Postgres and everything retained in it. Deleting the cluster removes the volumes too. Retention is not a backup: Steadmesh has no built-in backup or restore yet, so take your own (a Postgres dump does not include seat workspace volumes) before destroying anything you want to keep. GitHub personal access tokens you gave agents must be revoked at GitHub separately. See How do I take it down? and Where is the data stored?

Check the context and directory first, then destroy the organisation, then the platform:

cd organisation && terraform destroy   # retires the seats; data retained
cd ../platform && terraform destroy    # deletes namespaces and the database

Keep a copy of both stages' state files until the destroy has finished. Do not delete state files to clean up after removing a cluster by hand.
